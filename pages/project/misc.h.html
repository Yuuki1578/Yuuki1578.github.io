misc.h

> Prelude

This is a small, header-only type of library for the C programming language. It targets all C compilers that follows the standard specification of C99 or ISO/IEC 9899:1999.
The idea is to combining basic features that's found in another languages, but not in C in a single file. Usually, C library consist of but not limited to:

  1. Header files

    The purpose of this file is to provide a public API to the programmer but hide the implementation details. This make sense if your library is proprietary, but open source library usually does this too.
    The extension of this files are *.h.

  2. Shared object

    This is the implementation of the library. It always contains symbols from the header files, but it can have an internal API that cannot be called from outside, like functions with the static keyword.
    This files commonly reside in system directories. On POSIX, it's at /usr/lib or /lib.
    The advantage is we can now have multiple software that depends on a single shared object that can run independently. I guarantee you that every software you ran, depends on the libc shared object.

> Problem

Take example, libcurl, what do you need to setup in order to use the library? Of course, it's the shared object and the header files (maybe it's on different package like libcurl-devel and so on). That's not a problem, but if the library you are using also depends on the other library, and they're also depends on yet another library, what would you do? Heck, the package manager manages them all, no problem.

But what if you want to share your software to other people? They might use different machine architecture, or even different operating system. Maybe they had the library your software depends on in their package manager and maybe not. Now you have to tell these people to download the correct dependencies in order to just run your software. That doesn't sounds like a good user experience to me, there's a lot of moving parts that the users wasn't supposed to know in the first place.

> Solution

All of this actually can be solved if the library stick to the standard specification of the language itself. We can go further, if we can standarized a common features like networking, file system, and others, you can compile your software for every OS/Architecture that only depends on the language standard implementation, namely libc. But as suck as it is, they just say NO. Now we have different kind of system call that also differ with each architecture and OS.

> So what? Lmao

misc.h itself isn't trying to become the common standard of the C programming language, no no no. It just provide you an API that is common in another language and it's OS-agnostic.

Though, this is not the first time this idea came out. I took inspiration from the same library that's trying to solve the same problem like stb.
